# ANALYTICS

## Назначение

Этот документ описывает аналитику проекта: события, параметры, конверсии, воронки, метрики и правила интерпретации данных.

Он является source of truth для того, что измеряется и зачем.

## Цели аналитики

- Понять, доходят ли пользователи до основной ценности.
- Измерять конверсии в ключевых сценариях.
- Находить потери в воронках.
- Проверять влияние релизов.
- Отделять продуктовые проблемы от технических.

## Владелец и потребители

- Владелец документа и регулярного контроля: Analyst Agent.
- Product Manager Agent утверждает продуктовые определения метрик и принимает решения по рекомендациям.
- Tech Lead Agent и владельцы платформ отвечают за реализацию и исправление отправки событий.
- CEO Agent определяет приоритет действий по критичным аномалиям и конфликтующим целям.

### Правила доступа

- Доступ выдается Analyst Agent по принципу минимально необходимых прав и по умолчанию является read-only.
- Для Web используется персональная учетная запись с MFA.
- Для API используется отдельная сервисная учетная запись или ключ с минимальным scope; credentials хранятся вне репозитория.
- Аналитику не выдаются права публикации сборок, изменения цен и товаров, запуска production-конфигурации, управления пользователями или удаления данных.
- При изменении состава команды доступ отзывается владельцем системы; факт отзыва отмечается в реестре доступов [`../../05-operations/SECURITY.md`](../../05-operations/SECURITY.md).

## Ключевые метрики

| Метрика | Определение / формула | Где смотрим | Целевое значение |
| --- | --- | --- | --- |
| DAU | Уникальные активные пользователи за календарный день по принятому определению активности |  |  |
| WAU | Уникальные активные пользователи за последние 7 дней |  |  |
| MAU | Уникальные активные пользователи за последние 30 дней |  |  |
| Activation | Доля новых пользователей, достигших первого ценного действия в заданном окне |  |  |
| Retention D1 / D7 / D30 | Доля пользователей когорты, вернувшихся и выполнивших активное действие в заданное окно |  |  |
| Conversion | Пользователи, выполнившие целевое действие / пользователи, вошедшие в сценарий |  |  |
| LTV | Накопленная выручка на пользователя когорты за явно указанный горизонт |  |  |
| ARPU | Выручка за период / все активные пользователи за период |  |  |
| ARPPU | Выручка за период / платящие пользователи за период |  |  |
| First purchase conversion | Пользователи с первой успешной покупкой / пользователи выбранной когорты |  |  |
| Refund rate | Возвращенные транзакции или сумма возвратов / соответствующие покупки или выручка |  |  |
| Ad revenue | Рекламная выручка за период с указанным источником и валютой |  |  |
| Crash-free users / sessions | Доля пользователей / сессий без вылета |  |  |
| ANR rate | Доля затронутых Android-пользователей или сессий по принятому определению |  |  |
| Slow start rate | Доля запусков медленнее принятого порога |  |  |

Для retention обязательно указывать когорту и способ расчета, для LTV — горизонт и состав выручки, для ARPU/ARPPU — период, валюту и знаменатель. Метрика без зафиксированного определения не используется для управленческого решения.

## Сегменты

- Новые пользователи.
- Вернувшиеся пользователи.
- Платящие пользователи.
- Пользователи с ошибками.
- Пользователи по источнику трафика.
- Активные пользователи и пользователи с риском ухода по согласованному правилу.
- Пользователи по стране, платформе, устройству и версии.

Новые сегменты добавляются, если у них есть отдельная гипотеза или решение и достаточный размер. Сегмент не должен существовать только ради описательного отчета.

## Анализ поведения

Анализируются:

- частота использования функций и режимов;
- последовательности действий и время между ними;
- действия перед первой покупкой, возвратом, ошибкой или уходом;
- различия поведения между согласованными сегментами.

Анализ выполняется только для действий, по которым уже поступают корректные события. Если события отсутствуют, Analyst Agent предлагает имя события, момент отправки, параметры, владельца и критерий проверки, но не делает вывод о поведении.

## A/B-тесты

До запуска должны быть зафиксированы:

- гипотеза и единица рандомизации;
- контрольная и тестовая группы;
- одна основная метрика и защитные метрики;
- ожидаемый эффект, минимальный объем данных и длительность;
- сегменты, исключения и правило остановки;
- правило принятия решения.

Analyst Agent проверяет качество распределения групп, достаточность данных и влияние на защитные метрики. Если данных недостаточно, результат обозначается как незавершенный; отсутствие статистически или практически значимого эффекта не подменяется утверждением об улучшении.

## Анализ отзывов

- Похожие жалобы объединяются в темы по единому правилу классификации.
- Темы сравниваются по версии, стране, платформе и динамике количества/доли.
- Жалобы сопоставляются с известными ошибками, техническими метриками и изменениями релиза, если это возможно.
- Недельный summary содержит новые темы, растущие проблемы, затронутые сегменты и рекомендуемые действия.

## Ритм аналитики

### Ежедневно

1. Основные показатели, ключевые события, воронки и конверсии.
2. Качество и свежесть данных.
3. Поведение пользователей и основные сегменты.
4. Аномалии показателей.
5. Ошибки, сбои, ANR и медленные запуски.
6. Монетизация: покупки, подписки, возвраты и реклама.
7. Активные A/B-тесты.
8. Новые отзывы и повторяющиеся жалобы.

### Еженедельно

- динамика DAU, WAU, MAU, retention, LTV, ARPU и ARPPU;
- сравнение стран, устройств, версий, платформ и источников трафика;
- summary аномалий, релизов, монетизации, ошибок, экспериментов и отзывов;
- список рекомендаций, owners и статусов действий;
- предложения по новым событиям, воронкам, конверсиям, сегментам и A/B-тестам.

## Правила качества данных

- Не отправлять персональные данные без необходимости и правового основания.
- Не менять имена событий без миграционного плана.
- Не переиспользовать одно событие для разных смыслов.
- Любое новое важное событие должно иметь owner и цель.
- События монетизации должны соответствовать [`MONETIZATION.md`](MONETIZATION.md).
- Факты, интерпретации и гипотезы в отчетах разделяются.
- Поведенческий вывод допустим только при наличии соответствующих активных и проверенных событий.
- Для управленческого вывода всегда указываются источник, период, часовой пояс, baseline, фильтры и ограничения данных.
- Критичная аномалия эскалируется сразу, а не ждет регулярного отчета.
